# Property Management Platform Constitution

## Core Principles

### I. Centralized and Consistent Property Records

The platform MUST provide a single source of truth for properties, rentable resources,
tenants, stays, contracts, and rental payments.

- Records MUST maintain explicit relationships between these entities.
- Occupancy, availability, payment status, and contract status MUST follow documented
  business rules shared by the API, dashboard, and detail views.
- Dashboard totals and their linked lists MUST use consistent definitions and filters.
- Related changes MUST preserve data integrity, including when operations fail or
  concurrent updates occur.
- Redis and frontend caches MUST remain replaceable representations of authoritative
  PostgreSQL data.

This principle ensures consistent answers about who occupies a resource, which resources
are available, and which obligations remain outstanding.

### II. Backend-Owned API Contracts

The NestJS backend MUST own REST API definitions and generate the OpenAPI specification.

- The frontend MUST use the TypeScript client generated by `@hey-api/openapi-ts` for
  backend API communication.
- API request types, response types, and models MUST be generated from that specification.
- Developers MUST regenerate the client whenever the API contract changes.
- Generated client code MUST NOT be manually edited or replaced by independently
  maintained copies of API types.
- Contract changes MUST include corresponding documentation and verification of
  affected consumers.
- The backend MUST validate incoming requests independently of frontend validation.

The OpenAPI specification is the shared contract between frontend and backend.

### III. Deliberate Architecture and Durable Storage

Implementation MUST follow the approved technology stack and service boundaries.

- TypeScript and Bun MUST be used across frontend and backend.
- React and Vite MUST provide the frontend; NestJS MUST provide the backend.
- PostgreSQL MUST store application data, with Prisma as the ORM and Prisma Migrate
  managing schema changes.
- Uploaded documents MUST be stored in PostgreSQL as `BYTEA`, together with file metadata
  and applicable tenant/property relationships.
- Redis MUST support cache and temporary operational data, including rate limiting and
  background task status where needed.
- Frontend and backend MUST remain separately deployable services.
- New dependencies or architectural departures MUST have a documented need, rationale,
  and review. Departures from a governing requirement require an approved amendment.

Durable business records MUST remain recoverable independently of temporary caches.

### IV. Usable Across Devices and Themes

Every delivered user workflow MUST support mobile, tablet, laptop, and desktop use.

- Navigation, tables, forms, dialogs, charts, and dashboards MUST adapt to the viewport
  while preserving essential actions and information.
- All components MUST support consistent light and dark themes.
- Theme selection MUST support system preference detection, manual switching, and
  persistence across visits.
- Dashboard metrics MUST link to the relevant properties, resources, tenants, contracts,
  or payment records.
- Statuses and alerts MUST remain understandable in both themes and MUST NOT rely
  on color alone.

Responsive and theme support are acceptance requirements for each feature.

### V. Verifiable and Protected Business Operations

Business rules affecting occupancy, contract dates, rent amounts, or payment status MUST
have explicit acceptance scenarios and automated verification.

- Tests MUST cover relevant state transitions, date boundaries, invalid input, and
  failure cases.
- Changes spanning API contracts, database persistence, or document storage MUST include
  integration verification.
- Dashboard calculations MUST be checked against their underlying records.
- Access to tenant information and uploaded documents MUST be controlled by server-side
  authorization.
- Uploads MUST have documented size and type restrictions.
- Secrets, document contents, and sensitive tenant information MUST NOT appear in
  application logs.
- Completion claims MUST identify the checks performed and any remaining limitations.

Authentication methods, roles, and access boundaries MUST be defined before implementing
dependent workflows. These rules protect business records and make delivery verifiable.

## Technical and Operational Constraints

The approved stack is:

| Area | Required approach |
| --- | --- |
| Frontend | TypeScript, Bun, React, Vite |
| UI | Tailwind CSS and shadcn/ui |
| Server state | TanStack Query |
| Local/global state | Zustand when needed |
| Forms | React Hook Form and Zod |
| Backend | TypeScript, Bun, NestJS |
| API | REST, generated OpenAPI, Swagger UI |
| Client generation | `@hey-api/openapi-ts` |
| Database | PostgreSQL, Prisma, Prisma Migrate |
| Temporary data | Redis |
| Document storage | PostgreSQL `BYTEA` and metadata |
| Containers | Docker |
| Local services | Docker Compose: frontend, backend, PostgreSQL, Redis |

File metadata MUST include file name, file type, MIME type, file size, upload date, and
applicable tenant/property relationships. Storage MUST support rental contracts, tenant
documents, receipts, and property-related files.

Development, staging, and production MUST use separate environment configuration through
environment variables and `.env` files where applicable. Secrets MUST remain outside
version control.

Database and document-storage changes MUST document migration steps, data preservation,
and recovery considerations.

Dependency versions and compatibility MUST be recorded during implementation planning.
This constitution does not establish unverified version pins.

## Development Workflow and Quality Gates

1. **Define behavior.** Each feature MUST trace to an approved requirement and include
   measurable acceptance scenarios. Unresolved business rules MUST remain explicit.
2. **Check the constitution.** Plans MUST assess every applicable principle before
   research and again after design.
3. **Prepare implementation.** Tasks MUST identify dependencies, ownership, acceptance
   criteria, and required verification. Constitution-required tests MUST be included even
   when a generic template would otherwise treat tests as optional.
4. **Verify delivery.** Affected type checks, builds, automated tests, and UI checks MUST
   pass before completion is reported. Documentation-only changes require consistency
   review and relevant static checks; application tests are required only when behavior
   or an executable contract is affected.
5. **Review independently.** QA MUST compare implementation against approved requirements
   and test evidence before the requirement is accepted. Checks performed by a coding
   agent MUST NOT be presented as independent QA approval.

The repository's shared QA retry gate MUST be checked through `qa_state.py status` before
new development work or dispatch. A retry count greater than three MUST halt the
development loop. Missing or unreadable state MUST block new development and dispatch.
Only QA's audited helper may record failures or reset the counter after requirement
comparison and tests both pass. Follow `AGENTS.md` and the shared
`.codex/agents/qa-agent/skills/qa-agent/references/pipeline.md` for runtime procedures.

Existing specifications and constitutions MUST remain protected unless an explicit
amendment is authorized. Agent dispatch MUST respect explicit user scope. Automatic
Coding and QA agent dispatch is disabled for the current user-directed planning workflow
until the user explicitly changes that instruction. A constitution review or update
alone MUST NOT start implementation or downstream agents.

### Specification Decisions Required Before Dependent Work

Feature specifications MUST resolve the following decisions before dependent
implementation. These are product/design decisions, not missing constitutional text.

- Whether "Checking Out" is a tenant status or a label derived from an expected
  departure date, and the allowed tenant/stay transitions.
- Occupancy rules, including shared rooms, overlapping stays, and availability dates.
- "Expiring Soon" and upcoming check-in/check-out thresholds.
- Rent periods, due dates, partial-payment/overdue precedence, currency, rounding,
  and timezone.
- Authentication, user roles, document access, upload limits, and retention.
- Expected data volume and measurable performance targets.

Affected planning or implementation MUST remain blocked until material decisions are
confirmed. Independent work may proceed within the user's authorized scope. Examples in
the PRD MUST NOT silently become numerical thresholds, status rules, or capacity limits.

## Governance

This constitution governs project specifications, implementation plans, tasks, and code
reviews. Product scope originates in `prd.md`; technical constraints originate in
`Architecture.md`. Conflicts MUST be surfaced for resolution rather than silently changing
either source or weakening this constitution.

Amendments MUST:

- Describe the proposed change and its rationale.
- Identify affected principles, documents, contracts, and implementation.
- Include migration or compatibility considerations where applicable.
- Receive explicit project-owner approval before adoption.
- Update dependent planning guidance after adoption.

Constitution versions MUST follow semantic versioning:

- **MAJOR:** incompatible removal or redefinition of governing rules.
- **MINOR:** new principles or materially expanded obligations.
- **PATCH:** clarifications that preserve existing obligations.

Every implementation review MUST assess applicable constitutional requirements.
Exceptions MUST record scope, rationale, risk, approval, and a resolution condition.
An exception to a MUST requirement requires an explicit amendment; a plan's complexity
justification alone MUST NOT waive a governing rule.
